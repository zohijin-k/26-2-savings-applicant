# 실행 계획

예정 브랜치: `feat/savings-applicant-submit`. 선행 조건: 1단계 커밋 승인·완료, main 통합 또는 별도 기준 승인, 이 단계 계획·안내 문구·시험 기대값 명세 승인.

1. 사용자 승인 후에만 start/분기. 현재 main 기준 차이를 다시 읽는다.
2. 재업로드 허용 목록과 동일 selector를 신청자 finding/문서 차단에 적용한다. 원본 판정/저장/담당자 응답이 불변인지 합성 시험으로 비교한다.
3. 신청자 문서 상태를 중립 상태로 분리하고 타입·업로드/목록/마이페이지를 갱신한다. 인증/자가진단/경고/보완 응답의 숨은 자격 정보·차단도 정리한다.
4. 4단계 UI/라우트 정리, 3단계 준비상태·disabled 제출·수정 이동·서버 최신 재검사 연동.
5. 승인된 문구를 활용한 큰 모달·모든 서류 나열·재업로드 이동·접근성 구현.
6. test-impact.md의 사전 승인 범위만 기존 시험을 수정한다. 추가 발견은 이름·이유·변경 기대값을 따로 보고하고 승인 후 반영한다. 엔진/저장/담당자 단언은 보존.
7. 정상·모든 허용 사유·비허용 FAIL·모든 REVIEW·혼합 사유·레거시·교체/삭제·복수/동시 업로드·stale response·마이페이지 복원·직접 제출 API를 합성 검증한다.
8. 키보드 및 접근성 수동 확인: 처음 포커스, Tab 양방향 순환, Escape, 포커스 복원/업로드 이동, 배경 차단, 스크린리더 이름/구조. 실제 스크린리더 사용 불가 시 DOM/키보드 검증과 구분하여 한계 보고.
9. 1단계 implement.md의 네 갈래 전체 명령 재실행. 18개 시나리오와 각 집계/exit를 기록한다. 승인된 기대값 변경/추가 시험 수/skip 변동 분리 보고.
10. spec failure-filtering/pdf-form-workspace 등 변경된 신청자 계약만 정정. `git diff --check`, `git diff --stat main`, 결과·시험 영향·커밋 파일·메시지 보고 후 커밋 승인 대기.

## 신규 검증 항목
코드+severity 행렬/동일 코드 REVIEW 숨김/여러 허용 사유/허용+비허용 혼합/과거 code 없는 FAIL/상태와 finding 불일치/마스킹 불변/내부 판정 보존/비허용 FAIL 실제 접수 후 담당자 원값 조회/각 입력 차단/제출 직전 조건 변동/접근성 및 옛 최종확인 URL.
